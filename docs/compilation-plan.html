Compiling the meta-modeler's guide

The paper's figures are already a semantic layer of draft processes; a working compiler already turns five of them into running simulations. Here is the plan to finish the job — and to make the atlas a whole cell that lives, divides, and dies.

Source biology Agmon, A meta-modeler's guide to the cellular interface Repo viva-meta-modelers-guide Investigation paper-figures

In one paragraph

Agmon's paper argues that a cell is a set of interfaces whose internal mechanism can be refined or replaced while the interface is preserved — and it names, as a long-term goal, connecting a "biological semantic layer … to an executable layer containing the heterogeneous computational models that realize those descriptions." This repository has already built the semantic layer (Figures 4–10 as composites of draft processes) and a compiler between the layers — an algebraic effect system whose functor ⟦C⟧_H swaps each draft signature for a conforming Process handler while preserving the interface, with the paper's Fig 6 grain-swap as its worked example. Five of eleven figures now compile and run. This plan completes the remaining six, adds real-simulator handlers, and takes on the paper's hardest and most interesting figure — Figure 10 — where composition is no longer a static handler swap but an event-driven rewrite: division, development, evolution. That is exactly the control-flow half of algebraic effects, and the paper already supplies the mechanism for it (Fig 3c). The terminus is a composed, executable whole cell that senses its environment, maintains viability, and disintegrates or divides when its bounds are crossed.

1Where we already are

Two layers and a compiler between them — most of the scaffolding exists.

The paper's central claim is that biological organization is compositional: a cell is described from the outside by an interface (typed, unit-bearing exchange variables — chemical mol·s⁻¹, mechanical N, electrical A, thermal W, plus growth rate, shape, signaling, objective, and viability bounds), and from the inside by coupled processes that construct and maintain that interface. Its Table 1 gives this a formal spine, including the process-implementation mapping R_L — "the mapping from abstract processes to concrete mechanisms, linking model structure to executable behavior" — and states plainly that "this separation between compositional role and implementation is what allows a model component to be refined or replaced without rebuilding the entire system."

That mapping R_L is a compiler, and this repository has built it. The paper-figures investigation rebuilds Figures 4–10 as eleven process-bigraph composites of draft processes: typed ports plus a behavior contract (senses/affects/constraints), with a deliberately inert update — meaning without mechanism. compile.py then supplies the semantic→executable functor. 2The compiler we have, precisely

To plan the extension we need the current object stated exactly. A draft process is an effect signature op : (in : τ) ⇒ (out : τ); a handler is an executable Process whose ports match; a handler environment installs a handler (with config, initial values, and any declared store refinements) for each signature. compile_composite(C, H, core) is the functor ⟦C⟧_H: it walks the semantic composite and, for each draft node local:S with a handler in H, checks conformance H(S) ⊢ S, rewrites the node's address, and leaves every store and wire untouched. Four laws hold:

1 · Conformance. ⟦C⟧_H is defined only if the handler supplies every signature port with a compatible type (check_conformance).

2 · Interface preservation. interface_of(⟦C⟧_H) = interface_of(C) — port names and wired store paths are identical; only a declared refine may change a leaf's schema. This is the paper's central claim, made mechanical.

3 · Executability. the compiled composite builds and produces non-trivial dynamics; the semantic one is inert.

4 · Handler independence. two conforming environments give two executables sharing one interface — the Fig 6 grain-swap: one CoarseGrainedMetabolism signature handled by linear CoarseMetabolism (biomass = 5.0) or saturating KineticMetabolism (3.33), same ports.

This is a faithful, small algebraic effect system, and it exactly covers what the theory calls the handler-selection (tagless-final) regime: any forward-only interpretation of a signature. Every static figure — 4b, 5, 6, 7, 8, 9 — lives here. The plan's Phases 1–2 are "more handlers," no new machinery. Phase 3 is different in kind, and §4 explains why.

3The plan

Five phases. Phases 1–2 broaden handler coverage over the paper's static figures — the cheap, forward-only work. Phase 3 is the conceptual leap that Figure 10 demands. Phases 4–5 compose the atlas into a whole cell and ground its types in real ontologies.

1 · Handler coverage for the static figures

Finish Figures 7, 8, 9a

Pure handler-binding, no new compiler machinery — each is a conforming Process plus an environment entry plus a line in build_executables.py. Fig 7 (molecular mechanism): a reaction-network handler over the molecular interface (chemical/electrical/mechanical/thermal/structural ports; substrates/catalysts/cofactors/products subports) — reuse the pattern of the existing KineticReactionNetwork. Fig 8 (nested hierarchy): per-compartment process handlers (transmembrane transport, replication, metabolism, transcription, translation, subunit assembly) wired to the ECM→membrane→cytoplasm→nucleus→chromosome place graph — the interesting test of law 2 on a deep nesting. Fig 9a (coarse-graining stack): three handlers at three grains (molecular mechanism / self-organized process / coarse-grained process) over one interface, a second worked example of law 4 alongside Fig 6.

Deliverables: handlers_fig07/08/09a.py, three envs in handler_envs.py, three executables, three lines in BUILD; conformance + run covered automatically by tests/test_compilation.py. Risk: low.

2 · Real-simulator handlers

Make R_L point at genuine tools

The concept doc already anticipates this: "the same signature can later be handled by a real external simulator (COBRA/dFBA, tellurium/COPASI, …) — the swap is exactly a new, conforming handler, with the interface preserved by law 2." The paper's Discussion makes it the point: learned and mechanistic models alike "can occupy a process role within a larger composition when its inputs, outputs, assumptions, and domain of validity are made explicit." Wrap real engines behind the existing signatures, drawing on the sibling viva-* wrappers already in the ecosystem (viva-copasi, viva-comets for dFBA, viva-cobra-style FBA). The Fig 6 CoarseGrainedMetabolism signature gains a third handler — a real dFBA flux — and law 4 now demonstrates toy vs. real, not toy vs. toy.

Deliverables: at least one real-engine handler conforming to an existing figure signature; an env that selects it; a study comparing toy vs. real over the identical interface. Risk: medium — the wrapped tool's ports must be made to conform exactly (or via a declared refine).

3 · Event-driven rewrite handlers

Figure 10 — division, development, evolution

Here the static picture breaks. Division does not preserve the interface — it partitions one cell into two, each re-establishing its own interface (Fig 10b). Development embeds cells inside a new biofilm node (Fig 10d). Evolution adds a port (Fig 10f). These are the paper's event-driven graph rewrites (Fig 3c: divide / engulf / burst), and they need a handler that is not a structure-preserving Process but an orchestration Step that rewrites the place graph at runtime. This is a real extension of compile.py: a new handler class (a rewrite rule redex→reactum over stores) and a relaxation of law 2 from "interface identical" to "interface preserved up to a declared structural rewrite" — the same discipline as refine, applied to topology rather than a leaf. §4 argues this is exactly the algebraic-effect control-flow half, and that the paper already hands us the mechanism.

Deliverables: a RewriteHandler/Step abstraction; division as store-partition; development as hierarchical embedding; evolution as port addition; law 2′ (rewrite-aware interface preservation) with a test. Risk: high — the novel work; sequence it after Phases 1–2 prove the handler surface.

4 · Compose the atlas into a whole cell

Interface → coupling → viability → rewrite, in one run

The figures compile in isolation; the paper's thesis is that they compose. Wire the Fig 5 cell–environment coupling to the Fig 6 metabolism handler to the Fig 8 molecular hierarchy through their shared interface stores, producing one multiscale executable cell. Then add a viability monitor (Fig 4's viability bounds — temperature, pH, toxin concentration) as a Step that reads the interface and, when bounds are crossed, fires the Fig 6 disintegration rewrite (coarse cell → molecular network) or the Fig 10 division rewrite. This closes the paper's full arc — the cell as an agent whose description is valid only within its viability region, and which reorganizes when it is not — as a single running composite.

Deliverables: a composed whole-cell.composite.json (Fig 5+6+8); a ViabilityMonitor Step; a study showing a run that grows, crosses a bound, and disintegrates or divides. Risk: high — depends on Phases 2–3.

5 · Ontology-typed interfaces & provenance

Bind the vocabulary to real standards

The paper repeatedly points the interface vocabulary at existing ontologies: the Cell Behavior Ontology (CBO) for cellular behaviors, SBO for reactions/parameters, GO and ChEBI for molecular species, PDB/SMILES for structure. Bind the workspace's unit-bearing interface types (_types.py) to those terms, make check_conformance ontology-aware (a handler port conforms if its term is the signature's term or a subclass), and stamp each handler with provenance — which figure, which real tool, which assumptions and domain of validity (the paper's explicit requirement for a model to occupy a process role). This turns the atlas from a demonstration into a curatable, annotated resource.

Deliverables: ontology annotations on interface types; ontology-aware conformance; per-handler provenance records. Risk: medium — mostly integration, valuable for reuse.

4Figure 10 is the control-flow half of algebraic effects

The compiler today is an effect system in its interpreter-swapping sense: pick a handler, run each operation to completion, get a mechanism. Effect-handler theory calls the remaining power delimited continuations — a handler that captures "the rest of the computation" and may resume it zero times (halt) or many times (branch). A structure-preserving Process.update cannot do this; it returns deltas and control flows on.

The observation that organizes Phase 3

Cell division is multi-shot resumption. One cell becomes two, each continuing the computation with a partitioned share of state. Disintegration is zero-shot (the cellular description halts; control drops to molecules). Engulfment and bursting are structural resumptions with a changed place graph. These are precisely the continuations a run-to-completion handler lacks — and the paper already supplies the mechanism as a first-class construct: the event-driven graph rewrite of Fig 3c (divide / engulf / burst) and its orchestration. So Phase 3 is not bolting an alien feature onto the compiler; it is implementing the paper's own Fig 3c as the handler class that gives ⟦C⟧_H its control-flow half.

This reframes the whole plan cleanly. Figures 4–9 are the forward-only fragment: handler selection, interface preserved exactly (laws 1–4, done or Phase 1–2). Figure 10 is the rewrite fragment: orchestration handlers that transform the place graph under a declared structural rewrite, interface preserved up to that rewrite (law 2′, Phase 3). The atlas becomes complete only when both fragments are present — which is also the paper's own claim that composition is "not a property of a finished model but an ongoing practice" of refining, replacing, and re-cutting descriptions as their domains of validity change.

5How it lands in the investigation

The work threads through the existing paper-figures investigation and its fig-compilation study rather than starting new structure. Concretely:

  • Each new handler set extends fig-compilation's baselines with the freshly-materialized executable, and adds an image visualization pairing the semantic loom render with the executable one — the reader sees interface-preserved-but-mechanism-swapped at a glance.
  • Each figure's own study (fig-07, fig-08, …) graduates from "renders / structure-checks" to a Decide-phase verdict: does a conforming handler exist, does it run, does it preserve the interface? — the investigation's verdict_status moves from not-yet-run toward run.
  • Phase 3 warrants its own study (fig-10-rewrite) whose evaluation is law 2′: the rewrite changes exactly the declared structure and nothing else.
  • Phase 4's whole-cell composite becomes the investigation's headline result — the atlas's figures, composed and alive — surfaced on the read-only dashboard.

The compilation laws are the investigation's rigor spine: every executable is gated on conformance (law 1) and interface preservation (law 2/2′), so a handler that quietly changes the interface fails the build, not a reviewer's reading.

6Risks, gotchas, and sequencing

Known traps (already paid for once)

  • Init from _default, not _value. process-bigraph's realize initializes a typed leaf from _default; the draft composites' _value: 0.0 is inert, so every environment's init must set _default. Baked into _apply_store_overrides; new handlers must respect it.
  • Spatial fields are map[float], not array. a real spatial handler (Fig 5, and any Phase-2 reaction–diffusion) refines a scalar store to a length-N map[float] lattice — loom's map realizer adds element-wise (diffusion-delta semantics) and skips _-keys; array/list fail, and loom's SVG export can't snapshot a map-field node (it still builds and runs).
  • Conformance vs. refinement. a refined port's type legitimately differs from the signature's; the compiler auto-detects refined ports from the env's refine + wiring. Phase 3's structural rewrites need the analogous "declared, therefore allowed" discipline at the topology level.
  • Discovery + CI. static specs must live at <package>/composites/; README freshness and leaked-local-path guards in workspace-ci bite after composite edits — regenerate with vivarium-workbench gen-readme and keep render scripts path-relative.

Sequencing

Do Phase 1 first (it is nearly mechanical and completes the static atlas), then Phase 2 (one real handler is enough to prove the point and de-risk the wrapper path). Phase 3 is the research bet and should not block the others; prototype division alone before development/evolution. Phase 4 depends on 2–3; Phase 5 can proceed in parallel from the start, since ontology annotation touches types, not dynamics. A reasonable first milestone: all eleven figures with a conforming handler and a materialized executable (Phases 1–2 plus a minimal Phase-3 division), which makes the whole paper executable for the first time.
